# Firefox theming — Litho / Vellum / Daguerre / Verdigris

Firefox chrome (toolbar, tabs, urlbar, panels, sidebar, menus) themed with
`userChrome.css`/`userContent.css`, using the exact same four theme
families and role-based palettes as the rest of the desktop
(`~/.cfg-tzevaot/swaywm/`). Not a WebExtension theme, since that would need
the profile's `xpinstall.signatures.required` disabled to install
permanently on a standard (non-unbranded) Firefox build; userChrome.css
works on any build once one pref is set, and is what every other app in
this repo already does (hand-authored CSS/config per theme, not a plugin).

## Where the colors come from

Generated by `~/.cfg-tzevaot/bin/gen-browser-themes.py`, which imports the
same `PALETTES` dict `scheme_wallpaper.py` uses, so there's exactly one
place the hex values for a family/variant are defined. Re-run it after
changing a palette; it regenerates every variant from scratch. Don't
hand-edit the generated `userChrome.css`/`userContent.css` files, they'll
just get overwritten.

## Layout

```
firefox/
  litho/dark/userChrome.css, userContent.css
  litho/light/...
  vellum/dark/... , vellum/light/...
  daguerre/dark/... , daguerre/light/...
  verdigris/dark/... , verdigris/light/...
  active -> <family>/<variant>   (symlink; this is what the live profile imports)
```

Unlike the swaywm side (which needs a per-family `active` symlink *plus* a
sed-rewritten include line, because `sway/config` is a single tracked file
that can't itself be a symlink), Firefox's `active` is one flat top-level
symlink straight to `<family>/<variant>`. Switching either the family or
the variant is the same one-line repoint.

## Profile wiring (one-time, already done)

The live profile is `~/.mozilla/firefox/ep410r7q.default-release` (the one
tied to the manual install at `~/.firefox`, confirmed via its `lock`
file — Firefox also has a separate, currently-unused
`5gs66fhv.dev-edition-default` profile from another install, untouched).

```
<profile>/chrome/userChrome.css   -> @import "file://<home>/.cfg-tzevaot/firefox/active/userChrome.css";
<profile>/chrome/userContent.css  -> @import "file://<home>/.cfg-tzevaot/firefox/active/userContent.css";
<profile>/user.js                 -> user_pref("toolkit.legacyUserProfileCustomizations.stylesheets", true);
```

The `chrome/*.css` files in the profile are permanent one-line stubs, only
the `active` symlink they import ever changes.

## Switching

Same four commands as the rest of the desktop — there's no separate
`firefox-theme` script, switching the desktop theme switches Firefox too:

```
litho-theme dark|light|toggle|status
vellum-theme dark|light|toggle|status
daguerre-theme dark|light|toggle|status
verdigris-theme dark|light|toggle|status
```

**Restart Firefox to see the change** — userChrome.css isn't hot-reloaded,
unlike waybar/mako/sway which the scripts reload live.

## Known limits

- `userContent.css` has only reached chrome-privileged/about: pages since
  Firefox 69, never ordinary websites — this was never going to theme the
  web, only Firefox's own blank/error/newtab-adjacent pages, and modern
  `about:newtab` (Activity Stream) mostly ignores it anyway since it's a
  locked-down privileged component. Not a bug, just what's left after
  Mozilla tightened that surface.
- Selectors target the current Proton-era chrome (`.tabbrowser-tab`,
  `#urlbar-background`, `.urlbarView-row`, etc.), stable for years across
  releases, but not guaranteed forever — if a future Firefox redesign
  changes internal class/id names, only this file needs updating, the
  palette itself doesn't move.
